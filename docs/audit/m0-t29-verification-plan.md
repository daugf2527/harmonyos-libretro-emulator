# M0-T29: Switch 单飞验证测试计划

**日期**: 2026-05-31  
**状态**: 📋 待执行  
**关联任务**: M0 任务 29 - Switch 单飞验证

---

## 1. 测试目标

验证 Switch 单飞机制（T26）、取消机制（T27）、失败恢复机制（T28）在真机环境下的正确性和稳定性。

### 核心验证点

1. **单飞机制**：高频点击同一游戏，验证防抖和去重生效
2. **队列机制**：快速切换不同游戏，验证只执行最后一个
3. **取消机制**：切换中途取消，验证状态恢复 INIT
4. **失败恢复**：模拟失败场景，验证自动恢复和重试
5. **稳定性**：长时间压力测试，验证无内存泄漏/崩溃

---

## 2. 测试环境准备

### 2.1 设备要求

- **设备**: HarmonyOS 真机（推荐 API 12+）
- **构建**: Debug 或 Release HAP
- **日志**: 启用 hilog 过滤（`hilog | grep -E "LibretroGame|NEW"`）

### 2.2 测试数据准备

准备以下测试 ROM：

| 类型 | 用途 | 示例 |
|------|------|------|
| **快速加载 ROM** | 正常切换测试 | GB/GBC 游戏（< 1MB） |
| **慢速加载 ROM** | 取消测试 | GBA/PS1 游戏（> 10MB） |
| **损坏 ROM** | 失败恢复测试 | 截断的 ROM 文件 |
| **不存在 ROM** | 失败恢复测试 | 删除的文件路径 |

### 2.3 日志监控命令

```bash
# 实时监控 Switch 相关日志
hdc shell hilog -x | grep -E "LibretroGame|NEW|Switch|Cancel|Recover"

# 过滤关键事件
hdc shell hilog -x | grep -E "switching|switchToken|pendingSwitch|retryCount"
```

## 3. 测试场景

### 场景 1: 高频点击同一游戏（防抖验证）

**目标**: 验证 600ms 防抖机制生效，避免重复启动

#### 测试步骤

1. 打开 LibretroGamePage
2. 选择一个快速加载的 ROM（如 GB 游戏）
3. **快速连续点击"启动"按钮 10 次**（间隔 < 100ms）
4. 观察日志和 UI 状态

#### 预期结果

- ✅ **日志**: 出现 `启动请求过于频繁，已防抖忽略` 日志（至少 8 次）
- ✅ **UI**: 只执行 1 次切换，`switching` 标志只闪烁 1 次
- ✅ **状态**: 游戏正常启动，无重复 stop/start 抖动
- ✅ **性能**: 无卡顿，UI 响应流畅

#### 验证要点

- [ ] 日志中 `startOrSwitchGame` 调用次数 ≤ 2（第 1 次 + 防抖后 1 次）
- [ ] 日志中无 `RecoverAfterSwitchFailure` 调用
- [ ] 游戏画面正常显示
- [ ] 音频正常播放

---

### 场景 2: 快速切换不同游戏（队列验证）

**目标**: 验证 `pendingSwitch` 队列机制，只执行最后一个请求

#### 测试步骤

1. 准备 4 个不同的 ROM（A、B、C、D）
2. 启动游戏 A，等待完全加载
3. **快速连续切换**: A → B（点击后立即） → C（点击后立即） → D
4. 每次点击间隔 < 200ms
5. 观察最终运行的游戏

#### 预期结果

- ✅ **日志**: 
  - 出现 `切换中，记录待切换请求` 日志（2-3 次）
  - `pendingSwitch` 被多次覆盖
  - 最终只执行 D 的切换
- ✅ **UI**: 最终显示游戏 D 的画面
- ✅ **状态**: B 和 C 被跳过，不执行
- ✅ **Token**: 日志中 `switchToken` 递增 4 次

#### 验证要点

- [ ] 最终运行的游戏是 D（通过 `currentCore` 和 `currentRom` 确认）
- [ ] 日志中 B 和 C 的 `SwitchGameAsync` 未执行或被取消
- [ ] 无崩溃，无状态错乱
- [ ] 游戏 D 正常运行

---

### 场景 3: 切换中途取消（取消机制验证）

**目标**: 验证取消按钮功能，状态恢复到 INIT

#### 测试步骤

1. 选择一个**慢速加载的 ROM**（如 PS1 游戏，> 10MB）
2. 点击"启动"按钮
3. 在加载过程中（`switching = true`），**点击"取消"按钮**
4. 观察 UI 和日志

#### 预期结果

- ✅ **UI**: 
  - 取消按钮出现在左上角（红色边框）
  - 点击后按钮消失
  - `switching` 标志重置为 false
  - `switchError` 清空
- ✅ **日志**:
  - 出现 `Cancel switch requested` 日志
  - 出现 `CancelSwitch: incremented token` 日志
  - 出现 `Message: Cancel Received` 日志
  - 出现 `Cancel: resetting from state=X` 日志
  - 出现 `Reset() completed, engine back to INIT` 日志
- ✅ **状态**: 引擎回到 INIT，可以重新启动

#### 验证要点

- [ ] 取消按钮在 `switching = true` 时显示
- [ ] 点击取消后，加载立即停止
- [ ] 日志中 `switchToken` 递增
- [ ] 引擎状态回到 INIT（通过后续启动验证）
- [ ] 无资源泄漏（可以正常启动其他游戏）

---

### 场景 4: 模拟失败场景（失败恢复验证）

**目标**: 验证失败后自动恢复到 INIT，支持重试

#### 子场景 4.1: 加载不存在的 Core

**步骤**:
1. 修改代码，临时将 core 路径改为不存在的文件
2. 尝试启动游戏
3. 观察恢复过程

**预期结果**:
- ✅ 日志出现 `switch_load_core_failed`
- ✅ 调用 `RecoverAfterSwitchFailure`
- ✅ 引擎回到 INIT
- ✅ UI 显示错误信息

#### 子场景 4.2: 加载损坏的 ROM

**步骤**:
1. 准备一个截断的 ROM 文件（前 1KB）
2. 尝试加载该 ROM
3. 观察恢复过程

**预期结果**:
- ✅ 日志出现 `LoadGame failed` 或 `switch_load_game_failed`
- ✅ 调用 `RecoverAfterSwitchFailure`
- ✅ 引擎回到 INIT
- ✅ 可以加载其他正常 ROM

#### 子场景 4.3: 重试次数限制

**步骤**:
1. 使用损坏的 ROM
2. **连续点击启动按钮 5 次**（每次等待失败后再点击）
3. 观察重试行为

**预期结果**:
- ✅ 第 1 次失败：`retryCount = 0`
- ✅ 第 2 次重试：日志出现 `切换失败，准备重试 (1/2)`
- ✅ 第 3 次重试：日志出现 `切换失败，准备重试 (2/2)`
- ✅ 第 4 次：日志出现 `切换失败且已达最大重试次数 (2)，放弃重试`
- ✅ UI 显示：`切换失败: xxx (已重试 2 次)`
- ✅ 不再继续重试

#### 验证要点

- [ ] 所有失败场景都调用 `RecoverAfterSwitchFailure`
- [ ] 引擎状态正确恢复到 INIT
- [ ] 重试次数限制生效（最多 2 次）
- [ ] 错误信息清晰，包含重试次数
- [ ] 失败后可以加载其他游戏

---

### 场景 5: 混合场景（综合验证）

**目标**: 验证复杂交互下的稳定性

#### 子场景 5.1: 成功 → 失败 → 成功

**步骤**:
1. 启动游戏 A（正常 ROM）→ 成功
2. 切换到游戏 B（损坏 ROM）→ 失败
3. 切换到游戏 C（正常 ROM）→ 成功

**预期结果**:
- ✅ A 正常运行
- ✅ B 失败，调用恢复
- ✅ C 正常运行
- ✅ 状态转换：RUNNING(A) → STOPPED → INIT → RUNNING(C)

#### 子场景 5.2: 高频切换 + 取消

**步骤**:
1. 快速点击 A → B → C
2. 在 C 加载过程中点击取消
3. 立即启动游戏 D

**预期结果**:
- ✅ A 和 B 被跳过（pending 覆盖）
- ✅ C 开始加载
- ✅ 取消 C，状态回到 INIT
- ✅ D 正常启动

#### 子场景 5.3: 失败 + pending 队列

**步骤**:
1. 启动游戏 A（损坏 ROM）
2. 在 A 失败恢复过程中，快速点击 B → C
3. 观察最终执行的游戏

**预期结果**:
- ✅ A 失败，开始恢复
- ✅ B 被记录到 `pendingSwitch`
- ✅ C 覆盖 B（pending 只保留最后一个）
- ✅ A 恢复完成后，自动执行 C
- ✅ C 正常启动

#### 验证要点

- [ ] 所有状态转换正确
- [ ] 无状态错乱（如 `switching` 卡在 true）
- [ ] 无资源泄漏（可以连续切换多次）
- [ ] 日志完整，无异常错误

### 场景 6: 长时间压力测试（稳定性验证）

**目标**: 验证无内存泄漏、无崩溃

#### 测试步骤

1. 准备 10 个不同的 ROM（正常 + 损坏混合）
2. **循环执行 100 次切换**：
   - 随机选择一个 ROM
   - 启动游戏
   - 等待 2-5 秒（随机）
   - 切换到下一个游戏
3. 每 10 次切换记录一次内存使用
4. 观察是否有崩溃或卡死

#### 预期结果

- ✅ **稳定性**: 100 次切换无崩溃
- ✅ **内存**: 内存使用稳定，无持续增长
- ✅ **性能**: UI 响应流畅，无卡顿
- ✅ **日志**: 无异常错误或警告

#### 验证要点

- [ ] 完成 100 次切换无崩溃
- [ ] 内存增长 < 50MB（通过 DevEco Profiler 监控）
- [ ] 所有游戏都能正常启动和停止
- [ ] 日志中无 `FATAL` 或 `ERROR` 级别错误

## 5. 已知限制和注意事项

### 5.1 测试限制

1. **手工测试**: 所有测试均为手工执行，无自动化脚本
2. **时间依赖**: 某些场景依赖操作时机（如取消按钮点击时机）
3. **设备差异**: 不同设备的加载速度可能影响测试结果

### 5.2 测试注意事项

1. **日志过滤**: 使用 `grep` 过滤关键日志，避免信息过载
2. **内存监控**: 使用 DevEco Studio Profiler 监控内存
3. **多次验证**: 关键场景建议重复测试 3 次
4. **记录异常**: 任何异常行为都应记录日志和截图

### 5.3 不在测试范围内

以下场景不在本次验证范围：

- ❌ 多线程并发调用（NAPI 层已有互斥锁保护）
- ❌ 极端内存压力（如系统内存不足）
- ❌ 网络 ROM 加载（当前只支持本地文件）
- ❌ 多用户并发（单用户应用）
