## 4 个真实 H 级问题（必修）

### H-1: LibretroGamePage 字段路径赋值不触发响应（**真实功能 bug**）

**位置**:
- `entry/src/main/ets/pages/LibretroGamePage.ets:122` — `@State coreCheck: CoreCheckState = { running: false, text: '' }`
- 同上 `:123` — `@State soakState: RuntimeSoakState`
- 同上 `:132` — `@State perfDisplay: PerfDisplayState`
- 字段路径赋值多处：`:501`, `:513`, `:523`, `:532`, `:660`, `:666`, `:672`, `:678`, `:683`, `:684`, `:750-754`, `:1280-1282`

**症状**: ArkTS V1 的 `@State` 仅观察对象**第一层属性**，类似 `this.perfDisplay.coreFps = fps` 不会触发 UI 重渲染。

**根因**: ArkUI V1 状态管理对 plain interface 对象的字段路径赋值无法 hook（dependency collection 仅在 first-level setter）。

**3 种修复方案**:

**方案 A — 迁移 ArkUI V2（推荐，深度观察 + 无需拆组件）**:
```typescript
@ObservedV2
class PerfDisplayState {
  @Trace realtimeFps: number = 0
  @Trace coreFps: number = 0
  @Trace audioStatusText: string = ''
  @Trace perfStatsText: string = ''
  @Trace geometryText: string = ''
}

@Local perfDisplay: PerfDisplayState = new PerfDisplayState()
// 之后 this.perfDisplay.coreFps = fps 直接响应
```

**方案 B — V1 渐进（用 @Observed + @ObjectLink + 抽组件）**:
```typescript
@Observed
class PerfDisplayState { ... }

@State perfDisplay: PerfDisplayState = new PerfDisplayState()
// 消费此对象的视图必须抽独立 @Component，用 @ObjectLink 接收
```

**方案 C — 最简（整体替换，不重构）**:
```typescript
this.perfDisplay = {
  ...this.perfDisplay,
  coreFps: Math.round(fps),
}
```
缺点：触发整组重渲染，性能稍差。

**建议**: 同一组件的 3 个字段（coreCheck/soakState/perfDisplay）一起处理。可先用方案 C 快速止血，后续重构走方案 A。

### H-2: LibrarySearchPanel cachedSearchResults 是 private 而非 @State

**位置**:
- `entry/src/main/ets/pages/LibraryPage.ets` — `private cachedSearchResults`（持有数据，但未声明响应式）
- `entry/src/main/ets/components/LibrarySearchPanel.ets:18-21` — 子组件 `@Prop searchResults: LibraryRecord[]`

**症状**: 父组件 `cachedSearchResults` 是普通 `private` 字段，更新它**不触发父组件 re-build**，因此子组件 `@Prop` 永远拿不到新值。

**修复**（一行）:
```typescript
// 在 LibraryPage 中
@State private cachedSearchResults: LibraryRecord[] = []
```

`private` 是 ArkTS 访问可见性修饰符，不影响响应式装饰器。`@State private` 完全合法。

---

### H-3: LibretroNewArchTestPage build() 方法 723 行

**位置**: `entry/src/main/ets/pages/LibretroNewArchTestPage.ets:974-1697`

**症状**: 严重违反 `CLAUDE.md` 记录的 "build() 方法 ≤ 200 行" 上限。每次任意 @State 变化都重新执行整个 build()，增量渲染优化空间小。

**修复策略**:

1. 把 XComponent 区域、日志面板、控制面板、CoreOptions、Video/Audio 控制各自抽成独立 `@Builder` 方法
2. 复用部分抽成独立 `@Component` 文件（建议拆 3-5 个）
3. 高频复用的小块加 `@Reusable` 装饰器
4. 重复样式用 `@Styles` / `@Extend` 提取

**目标**: build() ≤ 200 行；初次拆分可分阶段：先抽出最大的 @Builder 块（>100 行的），再二次细分。

---

### H-4: RuntimeVirtualControllerLayer 方向键触控目标 24×24 vp

**位置**: `entry/src/main/ets/components/RuntimeVirtualControllerLayer.ets:61, 69, 87, 95`

**症状**: 方向键 ▲▼◀▶ 的尺寸参数全是 `24, 24`，低于 WCAG 2.2 最小 24 CSS px 的安全余量、低于 Android 48dp 和 Apple 44pt 建议。手指操作时容易误触/漏触，运动场景尤甚。

**修复（不改视觉，只扩响应区）**:
```typescript
this.RuntimeInputButtonById('up', '▲', '', 24, 24, 3)
  .responseRegion({ width: 44, height: 44, x: -10, y: -10 })
```

或在 `RuntimeInputButtonById` 内部统一加 `responseRegion` 让所有按钮的热区 ≥ 44vp。

## 16 个 M 级问题（按类别）

### 类别 1: @Prop 接复杂数组导致深拷贝（D1, D3, D6 + 其他）

**问题**: ArkUI 的 `@Prop` 对引用类型做深拷贝；父组件每次 re-build 时把数组深拷贝传给子组件。规模大时浪费明显。

**修复矩阵**:

| 子组件需求 | 推荐装饰器 | 原因 |
|------------|------------|------|
| 只读展示 | `@Prop` + **父侧缓存数组** | 父侧 `@State` 缓存避免每次 build 重新分配 |
| 双向变更 | `@Link` | 共享同一引用，无拷贝 |
| 嵌套对象 + 观察修改 | `@Observed` + `@ObjectLink` | 深度观察 + 引用共享 |
| 大型列表 (>50) | `LazyForEach` + `IDataSource` | 数据源持有数据，组件只引用 |

### 类别 2: 装饰性 ForEach 应迁 Canvas（P6, P7, P8）

**位置**:
- `entry/src/main/ets/components/LibraryDetailInfoPanel.ets:170-186` — 13 竖线 + 4 横线
- `entry/src/main/ets/components/RuntimePauseOverlay.ets:305-321` — 8 + 5 波形网格
- `entry/src/main/ets/pages/ShaderPreviewPage.ets:85` — 12 扫描线

**修复**: 复用项目已有的 `GridBackground` / `ScanlineBackground` Canvas 组件（CLAUDE.md 已记录的模式）。每处替换可消除 N 个装饰 Component。

### 类别 3: NAPI 同步调用阻塞 UI（N5）

**位置**: `entry/src/main/ets/pages/SaveStatePage.ets:249-251` — `nativeApi.refactoredSaveState()` 同步调用

**修复**: 改用 `runtimeSessionController.saveStateAsync()`（已存在的 wrapper），把大存档序列化卸到 napi async work，主线程不阻塞 16ms 帧预算。

### 类别 4: NAPI Promise 控制器模式（N7 + LibretroSwitchCoordinator）

**位置**: `entry/src/main/ets/common/LibretroSwitchCoordinator.ets:103-114` — `performClose` / `performSwitch` 无 try/catch

**修复模式**（来自社区最佳实践）:

```typescript
// 创建 Promise 时早 .catch() 兜底（避免 unhandled rejection 警告/崩溃）
const switchHandler = nativeApi.refactoredSwitchGameAsync(...)
switchHandler.catch((e) => hilog.warn('[switch] early-catch', e))

// 业务逻辑层 await + try/catch
try {
  const ok = await switchHandler
  // ...
} catch (e) {
  // 业务处理
}

// 并发场景用 Promise.allSettled，避免一个 reject 让其余成 unhandled
const results = await Promise.allSettled(napiCalls)
```

### 类别 5: i18n 资源体系（A1, A5, A3 + 多处硬编码）

**现状**: 项目无 `zh_CN/element/string.json`，111 处硬编码中文 Text。

**修复路径**:

```
entry/src/main/resources/
  base/element/string.json     # 默认回退
  zh_CN/element/string.json    # 简中
  en_US/element/string.json    # 英文（项目已有 README.en.md，应同步）
```

```typescript
// 旧
Text('游戏库')

// 新
Text($r('app.string.nav_library'))
```

动态切换：`I18n.System.setAppPreferredLanguage('zh-Hans' | 'en-US')`

**注意**: 这是 feature gap 而非 bug。是否落地取决于产品策略（仅中文 → 可暂缓；多语言市场 → 必修）。

## L 级问题综合建议

36 个 L 级问题不逐项处理，整体建议：

- **ForEach key 含 index（5 处）**: 这些场景大多不动态删中间项，**可忍受**
- **Ring-buffer 场景用 index key（P3/P9 logs 列表）**: 是合理的优化（移位时不重建组件），**不修**
- **微小开销 getter（P5）**: 单次开销 ~1 µs，**不修**
- **装饰性 ForEach < 15 项**: 影响有限，**低优先级**
- **`@Watch` 签名缺 propName**: ArkTS 当前可省略，但官方规范要求 `(propName: string) => void`，**规范修正**
- **缺 aboutToDisappear 的轻量组件（M1, M2）**: 没有显式订阅/定时器/资源时影响有限，**可忽略**

## Agent 报告质量评估

| 维度 | 子代理 | 修正后 | 主要偏差原因 |
|------|--------|--------|--------------|
| 性能反模式 | H4/M4/L2 | H1/M4/L5 | 子代理把 ring-buffer / 小规模数组等场景一律标 H |
| 装饰器 | H2/M5/L3 | H2/M3/L5 | D4 字段路径赋值评轻、D7 hudMetricsCache 评重 |
| 列表渲染 | H1/M4/L5 | H0/M0/L10 | 全部过激；keyGen 含 index 在不增删场景无害 |
| 生命周期 | H0/M3/L3 | H0/M0/L6 | M 全过激；缺 aboutToDisappear 但无资源的组件影响有限 |
| NAPI | H3/M4/L3 | H0/M5/L5 | 3 个 H 是 thin wrapper 合理设计，错误处理应在 controller 层 |
| a11y/i18n | H5/M4/L1 | H1/M4/L5 | 混合产品策略与技术 bug；i18n 是 feature gap |

**结论**: 子代理审查是高效的"广撒网"工具，但**严重度评估不可全信**。主代理（或人工）把关质检 + 联网核实是必要的下一步。
